    12. Conclusión

    Este documento describió el desarrollo de una aplicación web MVC con los frameworks [Spring MVC] y [Spring Boot] : una aplicación cuyas páginas HTML genera el servidor, mediante vistas [Thymeleaf], sin un framework [JavaScript] en el lado del cliente. Siguió paso a paso el curso [ASP.NET Core MVC], que a su vez se apoya en los cursos [NestJS] e Introducción a ASP.NET MVC mediante ejemplos: controladores y enrutamiento hacia vistas, formularios, internacionalización, seguridad y acceso a datos, seguidos de un caso de estudio completo.

    Los mismos 28 ejemplos y la misma aplicación se escribieron así con tres frameworks: [TypeScript], [C#] y [Java]. Los conceptos son los mismos; solo difieren los nombres y los mecanismos. Correspondencias entre [ASP.NET Core MVC] y [Spring MVC]:

    En cuanto a [ASP.NET Core], el punto clave que hay que tener en cuenta es:

    • [Spring Boot] configura la aplicación según las bibliotecas disponibles: basta agregar un starter para obtener un servidor web, un motor de vistas, una fuente de datos o una cadena de filtros de seguridad, que luego se pueden configurar mediante propiedades o declarando beans personalizados. Esto es muy eficiente, siempre que se sepa qué ha hecho [Spring Boot] por usted: el registro de inicio y el nivel [DEBUG] ayudan a averiguarlo;
    • gran parte del comportamiento depende de proxies: [@Transactional] o [@PreAuthorize] solo actúan cuando un método es llamado desde otro bean. Es importante saberlo para no ser tomado por sorpresa;
    • [Spring Data JPA] reduce la capa DAO a declaraciones: una interfaz, nombres de métodos que describen las consultas y, si es necesario, consultas [JPQL]. El bloqueo optimista ([@Version]) y la traducción de los errores de la base de datos a excepciones de [Spring] vienen incluidos;
    • [Spring Security] es más detallado que los atributos de [[Authorize]] en [ASP.NET Core], pero todo es configurable en [Java], en un mismo lugar: reglas de acceso por URL, lectura del token, redirecciones, cierre de sesión y protección [CSRF];
    • Las vistas de [Thymeleaf] son páginas HTML válidas que un navegador puede mostrar tal cual; solo contienen expresiones, ningún código [Java], lo que las mantiene simples. Por otro lado, no se compilan: un error en una expresión solo se hace evidente cuando se muestra la página, no durante la compilación como ocurre con [Razor].

    El caso de estudio muestra que una aplicación HTML clásica, sin el uso esencial de [JavaScript], sigue siendo una solución simple y robusta: cada página es una URL, el botón «Atrás» del navegador funciona y el servidor lo controla todo. El uso limitado de [JavaScript] (ventanas de confirmación) mejora la experiencia del usuario sin ser necesario para que la aplicación funcione.

    Para más información, consulte la documentación de [Spring Framework] (docs.spring.io/spring-framework/reference), así como la documentación de [Spring Boot] (docs.spring.io/spring-boot), [Spring Security] (docs.spring.io/spring-security/reference) y [Spring Data JPA] (docs.spring.io/spring-data/jpa/reference), el sitio de [Thymeleaf] (thymeleaf.org), y compare esta aplicación con sus equivalentes [ASP.NET Core MVC] y [NestJS].
